# Backend integration contract

Select `NEXT_PUBLIC_DATA_MODE=http` and `NEXT_PUBLIC_API_BASE_URL`; the default is `mock`. HTTP mode never falls back to demo data when an endpoint is missing. The Spring backend implements authentication, store settings, admin reads, categories, menu items, billing, and notification listing and acknowledgement. Inventory operations and automatic creation or resolution of stock alerts, reports, and admin user mutations remain unimplemented. Validate billing against a disposable MySQL database before using it for live sales.

Requests use credentialed cookies. Before unsafe requests, the client obtains a CSRF token from `GET /auth/csrf` and sends `X-XSRF-TOKEN`. On an expired access token it makes one coordinated `POST /auth/refresh` attempt and retries the original request after a successful refresh. A network failure during refresh is reported as a connection error rather than a logout. Checkout and daily usage send `Idempotency-Key`. Access and refresh tokens are never stored in localStorage. HTTPS, a unique JWT secret, secure cookies and non-default credentials are required for a real deployment.

Return JSON in the shapes defined by `src/types/domain.ts` and `src/services/api/types.ts` (numbers for DECIMAL within JavaScript safe precision, booleans for SQL flags, ISO UTC timestamps and `YYYY-MM-DD` business dates). Empty success may use 204. Errors use `{code,message,status,fieldErrors?,requestId}` and HTTP status; never leak secrets. `getMe` returns a public user, not `password_hash` or token hashes. The mock is for a single browser and does not provide secure auth or database transactions.

Checkout lines include `portion` and `expected_unit_price`. The server verifies each against the current catalog and rejects a changed price before collecting payment. Repeat an uncertain checkout with the same UUID key and unchanged request.

The table above fixes the expected names for this frontend; reconcile them with the Spring controllers before enabling HTTP. Uploaded images and server export helpers are exposed by `HttpPosApiClient` but the current admin picker stores data URLs and reports generate files in the browser. Wire the HTTP-mode UI to the multipart and download methods before production: SQL `image_path` is a path (max 512), not a data URL. Image uploads require server-side MIME and signature validation, size limits, authorization and persistent storage. Backend exports must apply the same filters and calculations.

Reporting views: `vw_daily_financial_summary` exposes business_date, sales_revenue, stock_used_cost, waste_cost, stock_adjustment_loss, operating_expense, contribution_after_stock_cost, estimated_operating_profit, waste_ratio_percent, estimated_operating_margin_percent. `vw_daily_menu_item_sales` exposes business_date, menu_item_id, item_name, quantity_sold, sales_revenue, quantity_missing_cost, estimated_item_cost, estimated_item_profit. API report DTOs additionally include purchase_cash_outflow, daily trend, ledger details and stock/waste joins as declared in domain.ts; purchases are not deducted from P&L.

Enums: roles ADMIN/BILLING/READ_ONLY (IDs 1/2/3); bills HELD/PAID/CANCELLED; payments CASH/UPI/CARD; units PACK/KG/LITRE/PIECE; stock movements PURCHASE/DAILY_USE/WASTE/OPENING/ADJUSTMENT_IN/ADJUSTMENT_OUT; alerts WARNING/CRITICAL and OPEN/RESOLVED; report periods DAILY/WEEKLY/MONTHLY/QUARTERLY/YEARLY/LIFETIME. No split payment, open registration, automatic BOM deduction or GST split.

## Phase 2 decisions

- Add a reviewed Flyway migration to snapshot `receipt_footer` and `cashier_name` on bills if historical receipt wording is required; the present schema does not snapshot them and current reprints can reflect later edits.
- V1 supports HELD, PAID and CANCELLED only. VOID/refund requires client sign-off and a separate schema/workflow; do not silently reinterpret paid bills.
- Move image validation/storage, Excel/PDF report generation, ledger and checkout transactions, idempotency, secure BCrypt/Argon2 passwords, authorization, pagination, and decimal arithmetic to Spring Boot/MySQL. Preserve immutable snapshots and never double count purchase cash outflow in P&L.
- JavaScript numbers and localStorage are demo limitations; validate decimal precision and use transactions/locking on the backend. Replace demo-only plaintext credentials and disable reset controls in HTTP mode.
